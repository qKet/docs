전체 구조

VPC 하나를 dev/prod가 공유하고(EKS 클러스터도 공유), RDS/ElastiCache/Secrets Manager만 환경별로 분리하는 구조입니다. private-data 서브넷은 인터넷 라우트가 아예 없어서 EKS 파드/bastion을 거치지 않고는 외부에서 절대 접근 불가합니다.

VPC (10.70.0.0/16)
│
├─ Public 서브넷 × 2 (2a, 2b)  ── IGW, NAT Gateway × 2, ALB
│
├─ Private-일반 서브넷 × 2 (2a, 2b)  ── EKS 노드그룹 / 파드
│    └─ 각 AZ 전용 NAT로만 아웃바운드 (cross-AZ 안 탐)
│
└─ Private-data 서브넷 × 2 (2a, 2b)  ── RDS, ElastiCache
     └─ 인터넷 라우트 없음 (완전 격리) — EKS 보안그룹 + bastion 보안그룹에서만 인바운드 허용

EKS 클러스터
├─ 노드그룹 (private-일반)
├─ aws-load-balancer-controller (Helm, kube-system)  → Ingress를 실제 ALB로 변환
└─ external-secrets (Helm, external-secrets 네임스페이스)
     └─ Secrets Manager(RDS 자동 시크릿 + connection 시크릿) → k8s Secret 자동 동기화

SSM bastion (private-일반)
└─ SSH 없이 SSM Session Manager로만 접속, RDS/Redis 터널링용

라우팅 테이블

  • public-rt — 0.0.0.0/0 → IGW (1개, 공유)
  • private-rt-2a / 2b — 0.0.0.0/0 → 각 AZ 전용 NAT (AZ당 분리)
  • private-data-rt — 로컬만, 인터넷 라우트 없음

게이트웨이

  • Internet Gateway × 1
  • NAT Gateway × 2 (AZ당 1개 + EIP)
NAT을 AZ별로 분리한 이유: cross-AZ 트래픽 비용 절감 + 한쪽 AZ 장애가 다른 AZ에 영향 안 주게

접근 제어

둘 다 private-data 서브넷에만 있고, 보안그룹이 EKS 클러스터 보안그룹과 SSM bastion 보안그룹발 인바운드만 허용합니다 (3306 / 6379). 인터넷 라우트 자체가 없어서 그 외 경로로는 원천적으로 접근 불가.

module.alb_controller terraform/modules/alb-controller

쿠버네티스 Ingress를 실제 AWS ALB로 만들어주는 컨트롤러. IRSA로 AWS 권한을 받음.

  • IRSA 역할: team5-qket-alb-controller-role — kube-system:aws-load-balancer-controller 서비스어카운트 전용, AWS 공식 정책 원본을 그대로 fetch해서 부착

접속 방법

kubectl 연결

aws eks update-kubeconfig --region ap-northeast-2 --name team5-qket-cluster

RDS/Redis에 직접 접속 (SSM 터널링)

aws ssm start-session --target <ssm_bastion_instance_id> \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["<rds_dev_endpoint>"],"portNumber":["3306"],"localPortNumber":["3306"]}'
모든 엔드포인트/ID는 terraform output으로 확인 (예: terraform output ssm_bastion_instance_id)
이 문서는 terraform/ 코드와 실제 AWS/쿠버네티스 상태를 기준으로 작성됨. 인프라 변경 시 수동으로 갱신 필요.
