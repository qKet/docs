# Qket 보안 및 권한 설계

이 문서는 Qket이 인증/인가/시크릿/네트워크 레벨에서 실제로 어떻게 보안을 설계했는지 정리한 것이다. 배경/트러블슈팅의 자세한 내용은 `CLAUDE_LLM_WIKI`를 참고.

## 1. 인증 (Authentication)

- **세션 기반 로그인** — 로그인 성공 시 서버가 `HttpSession`에 사용자 정보를 저장하고, 세션 자체는 Redis(Spring Session)에 보관한다. 클라이언트는 세션 쿠키만 들고 다닌다.
- **소셜 로그인** — Google/Kakao/Naver 3사 OAuth 지원. client-id/secret은 코드에 없고 Secrets Manager에서 읽어온다(4절 참고).
- **비밀번호 해싱** — BCrypt(`PasswordConfig`). 해시 문자열 자체에 라운드 수(strength)가 포함되어 있어서, 이후 설정을 바꿔도 기존 계정 해시는 그대로 유효하다(재해싱 불필요).

## 2. 인가 (Authorization)

### Role 모델

| roleId | 역할 | 접근 가능 경로 |
|---|---|---|
| 1 | 일반 회원 | 일반 API만 |
| 2 | 매니저 | `/manage/**` + 일반 API |
| 3 | 관리자 | `/admin/**` + `/manage/**` + 일반 API |

### 중앙집중형 인터셉터

`AdminAccessInterceptor`가 `/admin/**`·`/manage/**` 요청을 컨트롤러에 도달하기 전에 한 곳에서 걸러낸다. 예전에는 각 관리자 컨트롤러가 메서드마다 권한 체크를 개별적으로 넣었는데, 새 API를 추가할 때 이 체크를 빠뜨리면 그대로 인가 우회가 되는 구조였다 — 인터셉터 하나로 통합해서 "체크를 깜빡하는 실수" 자체가 안 나게 만들었다.

> ⚠️ **이 통합 자체가 단일 장애점(SPOF)이 될 수 있다는 게 실제로 드러난 적이 있다.** 2026-08-21, `getRequestURI()`(context-path `/api` 포함)로 경로를 읽어서 `"/admin"` 접두어 매칭이 절대 성립하지 않았던 버그가 있었다 — 로그인 없이도 관리자 API(카테고리/사용자/프로그램/메뉴/예약이력/공연관리) 전체를 조회·등록·수정·삭제할 수 있었던 치명적 상태였다. `getServletPath()`(context-path 제외)로 교체해서 해결([qKet/backend#41](https://github.com/qKet/backend/pull/41)). **교훈**: 인가 체크를 하나로 통합할 때는 그 하나가 뚫리면 전체가 뚫린다는 전제로, 실제 배포 도메인에 인증 없이 직접 호출해보는 통합 테스트가 필수다.

## 3. 네트워크 레벨 보안

- **관리자 도구 접근 제한** — Grafana/ArgoCD/dev 환경(`grafana.jun979.click`, `cd.jun979.click`, `dev.jun979.click`)은 공개 ALB가 아니라 IP 허용목록이 걸린 전용 ALB(`admin-alb`)로만 접근 가능. 허용 IP는 Terraform 변수(`admin_allowed_cidrs`)로 관리 — 실서비스(`app.jun979.click`)는 이 제한이 없다.
- **backend NetworkPolicy** — `backend-allow-same-namespace`가 backend 파드로 들어오는 트래픽을 같은 네임스페이스 + `monitoring` 네임스페이스(Prometheus 스크랩용)로만 제한. 그 외 네임스페이스에서는 backend에 직접 접근 불가.
- **Bastion 인바운드 없음** — SSM Session Manager로만 접속하는 구조라 인바운드 포트 자체가 열려있지 않다. SSH 키 배포/관리 자체가 필요 없다.
- **DB/Redis는 완전 격리된 서브넷** — private-data 서브넷은 라우팅 테이블에 인터넷 경로가 아예 없다(네트워크 구성도 참고). 보안그룹도 SG ID가 아니라 private-general 서브넷 CIDR로만 ingress를 허용.

## 4. 시크릿 관리

- **AWS Secrets Manager + External Secrets Operator(ESO)** — DB 자격증명(`db-secrets`), Redis(`redis-secrets`), 외부 API 키(`external-api-secrets`: Google/Kakao/Naver client-id/secret, Toss `TOSS_SECRET_KEY`)를 코드나 Git에 두지 않고 Secrets Manager에 저장, ESO가 K8s Secret으로 자동 동기화한다.
- **수동으로 채운 값 보호** — Secrets Manager의 시크릿 값(발급받은 실제 API 키 등)은 사람이 콘솔에서 직접 채우는데, Terraform이 재적용될 때 빈 값으로 덮어쓰지 않도록 `lifecycle { ignore_changes = [secret_string] }`으로 보호한다.
- **알려진 트레이드오프** — ESO 기본 재동기화 주기가 1시간이라, Secrets Manager 값을 콘솔에서 직접 바꾼 직후엔 `kubectl delete secret <name>`으로 강제 재동기화하지 않으면 K8s Secret이 최대 1시간 동안 옛날 값을 들고 있을 수 있다(실제로 결제 401/취소 오류로 재현된 적 있음).

## 5. IAM / 자격증명 — "장기 자격증명을 코드/시크릿에 두지 않는다"

이 원칙 하나가 아래 세 가지 결정에 공통으로 깔려 있다.

- **IRSA (IAM Role for Service Account)** — backend(S3 업로드), ALB Controller, External DNS, ESO, Karpenter, Grafana(AMP 조회) 등 AWS API를 호출해야 하는 모든 파드가 고정 액세스 키 대신 자기 ServiceAccount에 연결된 IAM Role의 임시 자격증명을 쓴다.
- **GitHub Actions OIDC** — CI가 AWS에 인증할 때 장기 액세스 키를 GitHub Secrets에 두지 않고, OIDC로 그때그때 임시 자격증명을 발급받는다. (다만 커스텀 claim(`repository`/`ref`) 조건이 이 계정에서만 원인불명으로 막혀서, 현재는 `sub` + 정확한 조직/레포 불변 ID로 우회 중 — 자세한 시행착오는 위키 `troubleshooting/github-actions-oidc-not-authorized` 참고.)
- **GitHub App (PAT 대신)** — CD 레포에 이미지 태그를 write-back하는 CI가 개인 접근 토큰(PAT) 대신 GitHub App을 쓴다. PAT는 개인 계정에 묶인 장기 토큰이라 그 개인이 조직을 나가면 깨질 수 있고 폐기도 수동으로 해야 하는데, GitHub App은 조직 소유라 그 리스크가 없다.

## 6. 알려진 리스크 / 향후 과제

- **BCrypt strength를 6으로 낮춤(시연용)** — 로그인 폭주 시 CPU 부하를 줄이려고 기본값(10)보다 낮춤. 기존 계정 해시는 그대로 유효하지만, 유출 시 크랙 난이도도 같이 낮아지는 트레이드오프가 있다 — 실서비스라면 10~12 권장.
- **`admin_allowed_cidrs` 수동 관리** — 팀원 IP가 바뀌면 사람이 직접 Terraform 변수를 고쳐야 한다. `/32` 누락 시 malformed CIDR로 관리자 도구 전체가 다운된 적이 있다(`troubleshooting/admin-alb-malformed-cidr-fixed-response-500`).
- **Redis에 AUTH 토큰 없음** — 세션/대기열 Redis가 VPC 내부 전용이라는 전제로 비밀번호 없이 운영 중. 격리된 서브넷 안이라 위험은 낮지만, 인증 계층 자체가 없다는 점은 인지하고 있어야 한다.
- **Alertmanager 알림 채널 미설정** — 모니터링 스택에 Alertmanager가 기본값으로 떠있지만 Slack/이메일 등 실제 알림 채널 연결이 안 되어 있어서, 알람 규칙이 있어도 아무에게도 전달되지 않는다.
