🔄 Qket ArgoCD / CI-CD 파이프라인 설계

Terraform(Infra) → ArgoCD(qKet/CD) → 앱 배포까지 전체 흐름 정리. 아직 실제로 구현 전 — 머리 복잡할 때 이 문서로 전체 그림 다시 확인할 것.

전체 흐름 레포 역할 1단계 · Terraform 2단계 · ArgoCD 최초 배포 Sync Waves 3단계 · 정상 운영 GitOps Bridge (IRSA) 아직 안 한 것

01 전체 흐름

크게 세 단계. 1·2단계는 클러스터를 처음 띄울 때 한 번, 3단계는 개발자가 코드를 push할 때마다 반복.

STAGE 1

terraform apply

  • VPC, EKS 클러스터
  • IRSA Role 미리 생성 (modules/irsa)
  • ArgoCD 설치 (helm_release, 최초 1회)
→
STAGE 2

ArgoCD 최초 배포

  • qKet/CD 레포를 App of Apps로 sync
  • namespace/ingress/networkpolicy/service
  • alb-controller, Grafana, ExternalDNS
→
STAGE 3

정상 운영

  • push → CI 빌드 → ECR push
  • CI가 qKet/CD 이미지 태그 수정+커밋
  • ArgoCD가 변경 감지 → sync → rollout

02 레포 역할 최종 정리

"어디에 뭘 두는가"가 계속 헷갈렸던 부분 — 최종 확정.

Infra
Terraform만. VPC/EKS/IAM/IRSA/ArgoCD 부트스트랩. 앱이 뭘 하는지는 전혀 모름.
qKet/CD
ArgoCD가 보는 전부. 기본 k8s 셋팅(namespace/ingress/networkpolicy/service) + 서드파티 애드온 + 앱 배포 매니페스트(이미지 태그).
backend / frontend
각자 CI만. 빌드 → ECR push → qKet/CD에 태그 write-back. 배포 방법 자체는 모름.
qKet/.github
재사용 워크플로우(workflow_call) — 빌드/푸시/태그업데이트 로직을 한 곳에 모아 backend/frontend 중복 방지.

03 1단계 — terraform apply

Infra/platform에서 한 번. ArgoCD/애드온이 쓸 IRSA Role을 미리 만들어두는 게 핵심 — ArgoCD가 나중에 그 차트를 설치할 때 Role ARN을 바로 쓸 수 있어야 하기 때문.

만드는 것비고
VPC / 서브넷 / NAT / 라우팅modules/vpc+modules/subnet, NAT·라우팅은 root(platform/main.tf)에서 직접 (순환참조 회피)
EKS 클러스터 + 노드그룹modules/eks
IRSA Role들modules/irsa — alb-controller, ExternalDNS 등 애드온용. for_each 범용 팩토리
ArgoCD 설치helm_release, 최초 1회만. 이후 ArgoCD가 자기 자신도 App으로 self-manage 가능
ECRmodules/ecr, backend/frontend 공유 저장소

04 2단계 — ArgoCD 최초 배포 (App of Apps)

ArgoCD가 뜨면 root Application이 qKet/CD를 보고 하위 Application들을 한 번에 등록·동기화. 여기서부터 Sync Wave로 순서를 강제해야 함 (아래 05 참고) — 안 그러면 예를 들어 Ingress가 ALB Controller보다 먼저 뜨려고 시도해서 실패할 수 있음.

05 Sync Waves — 배포 순서 강제

ArgoCD는 기본적으로 리소스를 순서 없이 동시에 적용한다. argocd.argoproj.io/sync-wave annotation을 리소스(또는 Application)에 붙이면, 작은 숫자부터 먼저 적용되고 그 wave가 Healthy 상태가 될 때까지 다음 wave는 대기한다. 같은 wave 안의 순서는 보장 안 됨 — wave 간 순서만 보장.

wave -2
가장 먼저
Namespace다른 모든 리소스가 여기 들어감
wave -1
클러스터 애드온
ALB Controller나중에 Ingress를 실제 ALB로 만들어줄 컨트롤러 ExternalDNSIngress 생기면 자동으로 DNS 레코드 만들어줌
wave 0 (기본)
기본 리소스
NetworkPolicy ConfigMap / Secret Grafana(모니터링)다른 걸 막지 않음
wave 1
앱 워크로드
Deployment (backend) Deployment (frontend) Service
wave 2
마지막
IngressALB Controller(wave -1) + Service(wave 1) 둘 다 준비된 후에만 의미 있음
Healthy 확인 → 다음 wave  ·  Healthy 확인 → 다음 wave  ·  ...

실제 적용 방법 — 매니페스트(또는 ArgoCD Application)의 annotation에 숫자만 넣으면 됨:

# Namespace — 가장 먼저
apiVersion: v1
kind: Namespace
metadata:
  name: qket-release
  annotations:
    argocd.argoproj.io/sync-wave: "-2"

# Ingress — 가장 나중
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: qket-backend-ingress
  annotations:
    argocd.argoproj.io/sync-wave: "2"
    kubernetes.io/ingress.class: alb
참고: App of Apps로 여러 ArgoCD Application을 따로 나눴다면(예: "infra-addons" App, "app-backend" App), wave를 Application 객체 자체에도 붙일 수 있음 — 그러면 리소스 단위가 아니라 Application 단위로 순서가 강제됨. 지금 저희는 qKet/CD 하나로 통일했으니 리소스 레벨 annotation이 더 맞을 가능성이 높음(App 분리 여부는 아직 실제 구현 안 함).

06 3단계 — 정상 운영 (push 이후)

최초 배포 이후 반복되는 흐름. wave -2/-1(네임스페이스·애드온)은 이미 Healthy라 다시 안 건드리고, 보통 wave 1(Deployment)만 갱신됨.

1

개발자 push

  • frontend 또는 backend 레포
→
2

CI

  • 빌드 + ECR push
  • 태그: backend-<sha>
→
3

qKet/CD 커밋

  • CI가 이미지 태그만 수정
  • git commit + push
→
4

ArgoCD sync

  • 변경 감지
  • wave 1(Deployment)만 롤아웃

07 GitOps Bridge — IRSA Role ARN을 ArgoCD에 넘기는 법

Terraform이 만든 IRSA Role ARN(1단계)을, ArgoCD가 설치하는 Helm 차트(2단계)의 values에 어떻게 전달하나 — 아직 실제 구현 전.

방법설명
ConfigMap 경유Terraform이 클러스터 안에 ConfigMap으로 ARN을 써넣고, ArgoCD Application의 Helm values가 그 값을 참조 (gitops-bridge-dev/terraform-helm-gitops-bridge 참고)
Helm values 직접 주입ArgoCD Application 매니페스트의 helm.values에 ARN을 하드코딩/템플릿으로 직접 박음 (더 간단하지만 ARN 바뀌면 매니페스트도 같이 고쳐야 함)
