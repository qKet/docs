# 테스트 및 장애 대응

이 프로젝트의 핵심 과제는 "티켓 오픈런" 순간의 트래픽 폭주를 대기열로 버텨내는 것이었기 때문에, 테스트도 단위/통합 테스트보다 **실제 트래픽을 흉내 낸 부하테스트(k6)** 를 중심에 뒀습니다. 아래 1절은 실제로 적용한 부하테스트를 테스트케이스 형식으로 정리한 것이고, 2절은 그 부하테스트와 실제 운영 중에 발생한 장애를 증상 → 원인 진단 → 해결 → 재발 방지 순으로 기록한 것입니다.

## 2. 장애 대응

부하테스트 중 재현했거나 실제 운영 중 발생한 장애 7건을 심각도(보안 → 가용성 → 운영사고 → 성능/용량) 순으로 정리했습니다. 전체 원문은 [`CLAUDE_LLM_WIKI/wiki/troubleshooting`](https://github.com/qKet/CLAUDE_LLM_WIKI/tree/main/wiki/troubleshooting)에 있습니다.

### 2-1. [보안] 관리자 API 인가 완전 우회 — context-path 매칭 버그

**증상** 로그인을 안 했거나 일반 회원(roleId=1)인 사용자가 관리자 전용 API(`/admin/**`, `/manage/**` — 카테고리·사용자·프로그램·메뉴·예약이력·공연관리) 전체를 **아무 제한 없이 호출 가능**했음. 조회뿐 아니라 등록·수정·삭제까지 가능한 상태였음. 실제 배포본(`dev.jun979.click`)에서 인증 없이 `GET /api/admin/categories` 호출 시 `200 OK`로 데이터가 그대로 반환됨을 확인.

**원인** 컨트롤러마다 흩어져 있던 "로그인/관리자 권한" 체크를 `AdminAccessInterceptor` 하나로 통합하는 리팩터링을 하면서, `request.getRequestURI()`(context-path `/api` 포함)로 `"/admin"` 접두어를 매칭하려 했음. 실제 요청 경로는 `/api/admin/...`라 `"/admin"`으로 시작하지 않아 매칭이 단 한 번도 성립하지 않았고, 인가 검사 자체가 통째로 스킵됨. 인터셉터 하나로 통합한 게 단일 장애점이 되어, 그게 뚫리자 관리자 API 전체가 동시에 뚫린 것.

**해결** `getRequestURI()` → `getServletPath()`(context-path 제외, 실제 서블릿 매핑 기준 경로)로 교체. `backend` hotfix PR([#41](https://github.com/qKet/backend/pull/41))로 즉시 배포.

**재발 방지** 인가 체크를 인터셉터/필터 하나로 통합할 때는 그 하나가 유일한 방어선이 된다는 걸 인지하고, `context-path`가 적용된 실제 배포 환경에서 인증 없이 관리자 API를 직접 호출해보는 검증을 배포 후 필수로 수행하기로 함(컨트롤러 단위 테스트만으로는 인터셉터 체인의 실제 동작을 못 잡음).

### 2-2. [가용성] ALB 헬스체크 연쇄 장애 — 1만 명 오픈런에서 전체 다운

**증상** TC-03로 10,000명 부하를 걸었을 때, 가장 먼저·가장 많이 몰리는 "홈" 페이지 성공률이 10%까지 떨어짐(다운스트림 페이지보다 오히려 나쁨).

**원인 진단** CloudWatch로 타겟그룹 헬스 상태를 분 단위 조회한 결과, 동일 시각 backend/frontend 타겟그룹 모두 `HealthyHostCount = 0`(전멸)을 확인. `HTTPCode_ELB_5XX_Count`는 분당 최대 13,383건까지 튀었지만 `HTTPCode_Target_5XX_Count`(타겟이 직접 준 5xx)는 그 10분의 1도 안 됨 — 즉 타겟이 에러를 준 게 아니라 **ALB가 라우팅할 healthy 타겟 자체를 못 찾아서** 자체적으로 5xx를 낸 것.

**연쇄 반응(cascading failure) 메커니즘**
1. 요청 폭주 → 파드 CPU 포화, 응답 지연
2. 헬스체크도 5초 타임아웃 안에 응답 못 함 (특히 frontend는 헬스체크 경로가 `/` — 일반 트래픽과 완전히 동일한 무거운 SSR 페이지)
3. 30초 연속 실패(15초 간격 × 2회) → ALB가 unhealthy 판정, 로테이션에서 제외
4. 남은 파드가 더 많은 트래픽을 받아 곧 같이 타임아웃 → 또 제외
5. 도미노로 전부 빠지면 `HealthyHostCount = 0` → 그 순간 요청 100% 실패, 부하가 빠지면 복귀를 반복

**추가로 발견된 애플리케이션 레벨 원인 2건**
- backend: `management.server.port`를 지정하지 않아 actuator 헬스체크(`/api/actuator/health`)가 일반 요청과 **같은 워커 스레드풀**을 씀 → 비즈니스 요청이 몰리면 헬스체크도 같이 줄을 섬
- frontend: 홈/상세 페이지의 `fetch`가 전부 `cache: "no-store"`라 매 요청마다 backend 재왕복 + SSR 재렌더링 — 캐싱 부재가 동시 요청 수를 그대로 부하로 직결시킴

부수적으로 ArgoCD `repo-server`(리소스 request가 없는 BestEffort 파드)도 같은 노드 CPU 포화에 밀려 라이브니스 프로브 실패로 3회 재시작됨.

**해결/조치** frontend `no-store` → `next: { revalidate: 60 }`로 교체(반영·배포 완료). backend actuator 포트 분리와 frontend 전용 헬스체크 엔드포인트 신설은 GitHub 이슈([frontend#28](https://github.com/qKet/frontend/issues/28), [backend#29](https://github.com/qKet/backend/issues/29))로 트래킹.

**재발 방지** 애플리케이션 원인 2건 수정 후 2,000/4,000명 규모 재검증에서는 완전 다운이 재현되지 않음(1-2절 참고). ArgoCD 등 addon 컴포넌트에 최소 CPU/메모리 request 부여는 아직 미적용 상태.

### 2-3. [인프라 운영] destroy 순서 위반 — IAM 손상 + ALB/webhook 고아 리소스

**증상** `01_infrastructure`를 `02_k8s-addon`보다 먼저 destroy하다가 `module.eks`의 IAM Role/Access Entry까지 삭제된 시점에 `02_k8s-addon destroy`를 시도해 `AccessDenied: sts:AssumeRole` 로 완전히 막힘 — kubectl/helm provider의 인증 수단 자체가 사라진 상태.

**원인** `kubernetes`/`helm` provider가 인증에 쓰는 IAM Role이 그 provider가 관리하는 K8s 리소스들보다 먼저 사라짐. 동시에 EKS node group도 `DELETING`으로 넘어가고 있어 ALB Controller/ESO 같은 addon 파드도 곧 죽는 이중 위기였음.

**해결 (4단계)**
1. `terraform apply -target=...`로 방금 지워진 IAM Role/Access Entry 4개만 타겟 재생성해 kubectl 접근권 복구
2. ALB Controller가 드레인 중 죽어 정리하지 못한 ALB·Target Group 2개·Security Group 2개를 AWS CLI로 직접 삭제 (일부는 `revoke-security-group-ingress`로 참조 규칙부터 제거해야 삭제 가능했음)
3. Ingress/ExternalSecret 오브젝트가 `deletionTimestamp`는 찍혔지만 finalizer 때문에 영영 안 지워짐 — 원인은 컨트롤러 파드가 죽었는데 `ValidatingWebhookConfiguration`이 클러스터에 고아로 남아, API 서버가 "모든 변경은 이 webhook 승인 필요"로 계속 막았기 때문. webhook 설정 자체를 삭제해 데드락 해소
4. IAM Group에 소속된 사용자 5명을 `remove-user-from-group`으로 제거 후 재시도

**재발 방지** destroy 순서(`04_data` → `02_k8s-addon` → `01_infrastructure`)를 최우선으로 지킴. `kubectl_manifest` provider는 finalizer를 기다리지 않는다는 걸 확인해 Ingress 리소스를 `kubernetes_ingress_v1`(finalizer clear까지 실제로 기다리는 provider)로 교체하고, `depends_on = [module.alb_controller]`로 "컨트롤러가 살아있을 때 Ingress를 먼저 지운다"를 강제함.

### 2-4. [설정 오류] Admin ALB CIDR 오타 — dev 전체 500

**증상** `dev.jun979.click`의 모든 경로가 `HTTP 500`. 백엔드/프론트 파드는 `1/1 Running`, 재시작 0회로 애플리케이션 레벨 문제가 전혀 아니었음.

**원인 진단** `aws elbv2 describe-rules`로 실제 ALB 리스너 규칙을 직접 조회해 `dev.jun979.click`의 `/`, `/api/*` 규칙이 `fixed-response 500`으로 대체돼있음을 발견. ALB Controller 로그에서 `CIDR block 58.29.99.44 is malformed` 에러 확인 — `admin_allowed_cidrs` 변수에 IP 하나가 `/32` 없이 들어가 있어 AWS가 거부, 이후 이 Gateway의 보안그룹 규칙 재조정(reconcile) 자체가 계속 실패해 dev 라우팅이 정상 타겟그룹에 못 붙은 것. (K8s HTTPRoute 오브젝트 상태는 `Accepted: True`로 멀쩡해 보여서 `kubectl describe`만으로는 원인이 안 보였음.)

**해결** `58.29.99.44` → `58.29.99.44/32`로 수정, `terraform apply -target=module.gateway_api_admin` 즉시 적용.

**재발 방지** `admin_allowed_cidrs`에 IP 추가 시 `/32` 포함을 항상 확인. Gateway API/ALB Controller 조합에서는 K8s 오브젝트 상태와 AWS 쪽 실제 반영 여부가 분리될 수 있다는 걸 인지하고, 이런 괴리가 의심되면 ALB Controller 파드 로그와 `aws elbv2 describe-rules`를 직접 봐야 함.

### 2-5. [성능] HikariCP 커넥션 폭풍 — 관련 없는 서비스까지 같이 멈춤

**증상** k6로 로그인 1000명 부하테스트를 돌릴 때마다, 테스트 대상이 아닌 ArgoCD/Grafana 화면까지 같이 느려지거나 응답이 안 됨.

**원인 진단** CloudWatch로 RDS 지표를 먼저 의심했으나 CPU 9%대, 연결 수 51~61개로 전혀 힘들지 않았음. 실제 원인은 HikariCP `maximum-pool-size: 40 × replica 8개 = 최대 320개 연결` 구성 — 연결 "개수"가 한도를 안 넘었는데도, 부하가 몰릴 때 여러 replica가 동시에 새 커넥션을 다수 생성하는 동작 자체가 CPU를 크게 소모함. 당시 워커 노드가 t3.medium(버스터블)이라 CPU 크레딧이 노드 단위로 공유되는데, backend 파드들이 커넥션 생성으로 크레딧을 몰아 쓰면서 같은 노드의 ArgoCD/Grafana 파드까지 CPU를 못 받은 것. RDS 지표만으로는 전혀 안 드러나는, 노드 레벨 리소스 공유 문제였음.

**해결** HikariCP `maximum-pool-size`를 20 → 이후 `DB_POOL_SIZE=10`으로 축소 배포. "replica 수 × dbPoolSize"가 RDS `max_connections`를 넉넉히 안 넘도록 기준을 정함.

**재발 방지** 부하테스트 전 `replica 수 × dbPoolSize` 계산을 체크리스트화(`Infra/loadtest/README.md`에 명시). "관련 없어 보이는 서비스까지 같이 느려진다"는 증상은 노드 단위 리소스 공유를 의심할 신호로 문서화.

### 2-6. [용량] 대기열 `MAX_ACTIVE_USERS=10` 병목

**증상** 2,000명 규모 엔드투엔드 부하테스트(로그인→대기열→좌석선택→예매) 실행 시, 테스트 전체 시간(약 11분) 동안 **단 한 명도 대기열을 통과하지 못함**. 에러는 0건이라 서버가 죽은 건 아니었음.

**원인** `QueueServiceImpl.MAX_ACTIVE_USERS = 10`이 하드코딩되어 있어, 한 번에 활성화 가능한 인원이 10명뿐이었음. `처리량 ≈ MAX_ACTIVE_USERS ÷ 평균 활성 체류시간`인데 10명 슬롯으로는 2,000명을 감당할 회전율이 나올 수 없었음.

**해결** `MAX_ACTIVE_USERS`를 10 → 150으로 상향, hotfix로 즉시 배포. 재테스트에서 대기열 평균 대기 20.5초(최대 56초), 예매 성공률 99.85% 확보.

**재발 방지** 150은 2,000명 실측 데이터로 역산한 값일 뿐 "정답"이 아니며, 실제 서비스 규모(동시접속자 수·좌석 수·오픈런 시간대)에 맞춰 재계산이 필요함을 명시. 대기열이 있다고 무조건 트래픽을 막아주는 게 아니라 활성 슬롯 수 자체가 병목이 될 수 있다는 걸 실측으로 확인.

---

### 2-7. [성능] CPU 스로틀링 — "스로틀링 ≠ 사용률"

**증상** TC-02(1000명 부하테스트) 중 응답이 눈에 띄게 느려짐.

**원인 진단 (1차)** Prometheus `container_cpu_cfs_throttled_periods_total`(스로틀링의 결정적 신호, 단순 사용률과는 다름)을 조회해 5분간 1,500~2,300 periods 수준의 심한 스로틀링을 확인. 당시 backend CPU `request: 250m / limit: 1`이 BCrypt 해싱 연산(로그인 시 CPU를 상당히 씀) 앞에서 너무 작았음.

**해결 (1차)** `limit`을 1 → 2 CPU로 상향, 재테스트에서 스로틀링·응답시간 개선 확인.

**원인 진단 (2차)** 신규 Grafana 패널로 재관찰한 결과, CPU 스로틀링은 순간 파드당 최대 200까지 튀는데 노드 CPU 사용률은 30~35%대(전혀 포화 안 됨), HPA도 `cpu: 1%/70%`로 스케일아웃을 하지 않고 있었음. KEDA CPU 트리거는 limit이 아니라 **request 대비 5분 평균 사용률**을 보기 때문에, 순간 버스트는 평균으로 희석되어 스케일아웃 문턱을 못 넘는 것 — "파드 개수 부족"이 아니라 "개별 파드가 순간적으로 자기 CPU limit에 부딪히는" 문제였음.

**판단(권고, 2026-08-13 기준 미적용)** replica 수보다 개별 파드 CPU limit을 노드 여유에 맞춰 더 올리는 쪽(2 → 3~4)이 순간 스로틀링을 줄이는 데 더 직접적인 처방으로 판단, KEDA `maxReplicas` 조정은 평균 사용률이 실제로 70%에 근접하는 걸 관찰한 뒤로 보류.
